# LLM 复盘迭代闭环规格（S-20）

> 来源：用户 2026-09-17 凌晨提问「**我们的 LLM 能不能做到复盘分析迭代规则**」。
> 性质：架构级新件（M2 法案闭环的进化 —— 从「LLM 出一次法案」到「LLM 持续迭代法案」）。
> 分工：本件只出规格与判据；代码 / pipeline 归 zcode。

---

## 0. 结论（先回答"能不能"）

**能。** 且基础设施**绝大部分已就位**，缺的是最后一环：

| 环节 | 现状 | 证据 |
|---|---|---|
| ① LLM 能产出结构化决策 | ✅ 已跑通 | `overmind_lex_record.json` `"source": "llm"`，**1141 ms** 出完整 JSON（phase / threat / economy / priorities） |
| ② 管道能编译换版 | ✅ 已跑通 | rev 1→2→3；实机打出 `lex applied rev 3` |
| ③ 有模型上下文注入点 | ✅ 已有 | `overmind_play.py` 的 `model_context(state)` / `code_context(state)` |
| ④ **把"上一版跑得怎么样"喂给模型** | ❌ **缺失** | `model_context` 中**无** metrics / trend / 复盘数据 |
| ⑤ 迭代后效果验证 | 🟡 半有 | `--trend` 能出指标表，但未接入闭环 |

⇒ **本件要做的 = 补 ④，并把 ⑤ 接成环。**

---

## 1. 它在三条公理里的位置

| 公理 | 层级 | 机制 |
|---|---|---|
| A1 规则优先于计划 | 形态 | 规则（非时序指令） |
| A2 多线并行 | 执行 | 命中集全部推进 |
| **A3 看收益（游戏内）** | **月级** | streak 熔断 —— 没好处就停 |
| **A3′ 复盘迭代（游戏外，本件）** | **版级** | **LLM 看上版结果 → 改规则 → 换版** |

**A3 与 A3′ 是同一条原则的两个时间尺度**：
- A3（月级）在游戏内自动跑，处理"这个月该不该做"；
- A3′（版级）在游戏外由 LLM 跑，处理"**这套规则本身是不是错了**"。

> A3 只能让坏规则**停下来**，**不能让它变好** —— 变好必须靠 A3′ 的复盘迭代。
> 这正是用户提问的价值：**光有熔断不够，还要有进化。**

---

## 2. 闭环结构（五步）

```
① 采集  →  ② 复盘（LLM）  →  ③ 生成新规则集  →  ④ 换版  →  ⑤ 跑一段  →  回到 ①
                                                    ↑
                                            （需重载游戏，硬边界）
```

### ① 采集（数据契约 —— 关键：**结构化，不是原始日志**）

> ⚠️ 本地模型能力有限（1.1 s / 数百字符级输出），**绝不把几 MB 的日志塞给它**。
> 必须**先由脚本把表现压成一张小表**再喂。

给 LLM 的复盘输入（`ReviewInput`）建议字段：

| 字段 | 来源 | 例 |
|---|---|---|
| `rev` | 当前版本号 | 3 |
| `span` | 覆盖年份 | 2241–2246 |
| `metrics_trend` | `overmind_metrics.py --trend --resources` | districts 4→4、buildings 10→10、**fleet 0**、**consumer_goods 负值** |
| `waste` | 库存表 | **energy 25000 满仓**、food 15000 满仓 |
| `rule_hits` | 【求值】日志 | 各规则命中次数 |
| `gain_scores` | 【收益】日志 | 各相位收益分 +1/0/-1 |
| `fused` | 【熔断】日志 | 哪些相位被熔断、连续几月 |
| `errors` | error.log（仅涉本 mod） | Invalid macro ×4（D-21） |
| `known_defects` | BACKLOG 摘要 | D-27..D-30 中与决策相关的部分 |

**体积控制**：整份输入建议 **≤ 1500 字符**（与已验证的 485 字符出案能力同量级）。

### ② 复盘（提示词契约）

提示词必须让模型回答**三件事**（顺序固定，便于判据化）：

1. **诊断**：上一版哪些规则/相位没收益？可能原因？
2. **归因**：是规则写错了、还是外部条件（缺工程船 / 资源结构）？
3. **处方**：给出**新的规则集**（按 S-18 v4 数据契约：`cond/cond2/op/act` + `parallel_max` + 收益阈值）

> 与 A1 一致：**产出必须是规则，不是计划**（不得出现"第 N 月做 X"）。

### ③ 生成

复用现有 `model_context` → LLM → `compile_lex` 链路；
输出格式从「8 槽」改为「规则集」（S-18 §3.1 数据契约）。
失败降级 `code_context`（现有机制，保留）。

### ④ 换版

走现有 rev 严格递增通道（`overmind_play.py`，已就绪）。
⚠️ **硬边界**：`@om_lex_rev` 是**启动期常量**，换版后**必须重载游戏**才生效
⇒ **迭代周期受"用户愿意重载几次"约束**，不能设计成高频闭环。

### ⑤ 验证

重载后跑一段（建议 ≥10 游戏年），再用 ① 采集，对比：
- 被诊断的问题是否缓解（如：消费品不再为负、工程船保有量恢复）
- 新规则是否带来正收益（【收益】日志）

---

## 3. 约束（三条，实现前必须接受）

1. **换版需重载** ⇒ 迭代是**低频**的（每次用户重载一次才能迭代一轮）。
   设计目标不是"实时进化"，而是"**每轮重载都能比上一版更好**"。
2. **本地模型能力有限** ⇒ 输入必须**结构化 + 限长**；不要指望它自己归纳原始日志。
   若诊断质量不足，优先**改进输入摘要**，而不是换更大模型。
3. **不得因复盘而削弱 A3** ⇒ 游戏内熔断（A3）与游戏外迭代（A3′）**并存**，
   复盘不能关掉熔断（否则坏规则在下一版到来前会持续空转）。

---

## 4. 验收标准（交 zcode 实现时按此写守卫）

1. **采集可用**：`ReviewInput` 能由脚本从存档 + 日志生成，含 §2① 全部字段，体积 ≤1500 字符。
2. **注入生效**：`model_context` 确实带上复盘数据（注入"摘掉复盘段"→ 守卫失败）。
3. **产出合规**：LLM 输出仍为**规则形态**（注入"输出时序计划"→ 守卫失败，与 A1 一致）。
4. **可降级**：模型失败时走 `code_context`，不中断管道。
5. **闭环可验证**：给定一段"坏表现"输入（如消费品为负 + 无工程船），
   模型输出的规则集**必须针对该问题有明确动作**（人工判读 + 关键点断言）。
6. **换版合规**：rev 严格递增，走既有通道（与 M2-1 对齐）。

---

## 5. 与既有工作的关系

- **依赖** S-18 v4（规则集数据契约 + 求值器 + 收益门）—— 本件是它的**上游供给**；
- **复用** `overmind_play.py` 全链路、`overmind_metrics.py --trend`、现有 `model_context`；
- **强化** A3 —— 补上"让坏规则变好"的能力（A3 只能让它停下）；
- **不替代** A3 —— 两者并存（月级熔断 + 版级迭代）。

## 6. 待 zcode 确认

1. `model_context` 现有 payload 结构，复盘段如何接入最省事；
2. `ReviewInput` 各字段的**取数可行性**（尤其 `rule_hits` / `gain_scores` —— 需 S-18 的日志先落地）；
3. 本地模型的**输入长度上限**（决定摘要压到多短）；
4. 建议的**迭代触发时机**（用户重载时自动跑一次？还是手动 `--review`）。
