# 需求规格说明书（SRS）

项目：Stellaris Overmind · 版本 srs v1 · 2026-09-14
每条需求都可验收（有编号、有验收方式）。优先级：P0 必须 / P1 应该 / P2 可选。

---

## 1. 功能需求

### 1.1 决策层（大模型）

| 编号 | 需求 | 优先级 | 验收方式 |
|---|---|---|---|
| FR-01 | 系统能读取最新存档并抽取帝国状态（资源、星球、舰队、科技、传统、飞升、外交） | P0 | 单测：给定样例存档返回字段完整 |
| FR-02 | 系统能调用本地大模型产出**结构化战略**（优先级排序、威胁等级、经济瓶颈、姿态、方向） | P0 | 集成测试：provider 返回可解析 JSON；失败时回退到代码评估 |
| FR-03 | 大模型**永不直接产出脚本**；其输出只能落在封闭取值域内 | P0 | 单测：注入越界值 → 编译器拒绝 |
| FR-04 | 战略输出必须可审计：记录原始输出、编译结果、时间戳 | P1 | 检查 sidecar JSON 存在且字段完整 |

### 1.2 编译层（法案）

| 编号 | 需求 | 优先级 | 验收方式 |
|---|---|---|---|
| FR-10 | 能把结构化战略编译为**合法的 Clausewitz 脚本** | P0 | 单测：生成文本可被解析；语法元素齐全 |
| FR-11 | 编译产出的每个 ID（区划/建筑/zone/传统/飞升/战争目标/设计）都必须存在于游戏数据中 | P0 | 审计器对生成文件 0 违规 |
| FR-12 | 每版法案带**版本戳**，使重载后能自动顶替旧法案 | P0 | 单测：版本戳单调递增且写入全局变量文件 |
| FR-13 | 编译失败**不得**破坏游戏中已有的法案（要么整份替换，要么保留旧版） | P0 | 单测：非法输入 → 旧文件内容不变 |
| FR-14 | 法案覆盖面：至少包含 ①相位日程 ②资源缺口优先序 ③舰队姿态 ④专业区方向 ⑤传统顺序 ⑥飞升顺序 | P0 | 检查生成文件含全部变量与生成 effect |

### 1.3 执行层（游戏内）

| 编号 | 需求 | 优先级 | 验收方式 |
|---|---|---|---|
| FR-20 | 每月自动自检并行动，**无需玩家操作** | P0 | 实机：10 年长跑，存档指标增长 |
| FR-21 | 执行相位覆盖：经济救济、住房、就业/工业、民生、科研、军备 | P0 | 代码审查 + 实机 |
| FR-22 | 执行相位覆盖：**传统与飞升** | P0 | 实机：帝国获得传统与飞升天赋 |
| FR-23 | 执行相位覆盖：**战争与防御**（星港、陆军、轰炸姿态、战争目标） | P1 | 实机：一场战争中能推进战争目标 |
| FR-24 | 每次建造必须从国库扣除等价资源（不得凭空生成） | P0 | 单测费用表存在；实机看国库变化 |
| FR-25 | 每类动作每月最多触发一次（限额），避免脚本卡顿与刷屏 | P0 | 代码审查：限额标记齐备 |
| FR-26 | 只在玩家帝国生效（`is_ai = no`），不得影响 AI 帝国 | P0 | 代码审查 + 实机（AI 帝国行为不变） |
| FR-27 | 提供**零控制台**的开关（UI 可点） | P0 | 实机：edict 面板可点，状态随之改变 |
| FR-28 | 开关关闭后应停止全部自主行为，且不回退既有成果 | P0 | 实机 |

### 1.4 迭代闭环

| 编号 | 需求 | 优先级 | 验收方式 |
|---|---|---|---|
| FR-30 | 每次启动游戏前，能自动完成"读档 → 大模型 → 编译法案 → 启动"一条命令 | P0 | 实机：双击/单命令后进入游戏且法案已换版 |
| FR-31 | 能对比两次存档，量化自治成效（人口/区划/建筑/舰队/科技/传统） | P1 | 单测：给定两份快照返回差值 |

## 2. 非功能需求

| 编号 | 需求 | 验收方式 |
|---|---|---|
| NFR-01 | 回归测试全绿；新增模块必须有测试 | `pytest -q` 全通过 |
| NFR-02 | 脚本 ID 审计 0 违规（误报自身也是缺陷） | 审计器输出为空 |
| NFR-03 | 实机运行后游戏 `logs/error.log` 不得出现 mod 相关错误 | 读日志 |
| NFR-04 | 命名空间隔离：mod 新增 key 一律以 `overmind_` / `om_` 开头 | 全局搜索 |
| NFR-05 | 编译耗时 < 1s；审计耗时 < 30s（4.4.6 全量数据） | 计时 |
| NFR-06 | 所有结论区分「确证」与「推断」，确证给出来源 | 文档审查 |
| NFR-07 | 不引入高危手段（内存读写/DLL 注入/反作弊边界） | 代码审查 |

## 3. 验收标准（里程碑级）

| 编号 | 标准 | 对应里程碑 |
|---|---|---|
| AC-1 | 审计器 0 违规，且误报清零 | M1 |
| AC-2 | `pytest -q` 全绿且新增测试覆盖编译器与审计器 | M1 |
| AC-3 | 载入存档后 `error.log` 无 mod 报错 | M1 |
| AC-4 | 连续 ≥10 游戏年无人干预（F3' 协议按 12 年执行），帝国四类指标（区划/建筑/舰队/传统）满足 **AC-4 v2**：① 终值不低于初值；② 无 ≥3 个连续采样点的持续下降段；③ 冻结标「注意」（舰队冻结由 `om_ships_built` 交叉确证） | M1 |
| AC-5 | 每次重载后法案版本戳切换，在存档变量中可查 | M2 |
| AC-6 | 能自主宣战并推进战争目标至结束 | M3 |
| AC-7 | 覆盖动作清单七大领域 ≥ 60% 高频动作 | M4 |
| AC-8 | N 年长跑无存档损坏、无新增错误 | M5 |

> **修订 2026-09-15（D-13 决策 A，用户委托子智能体流程执行）**：AC-4 由「单调增长」改为上表 v2 三条。
> 原因：本模组全部建造动作挂在「出问题才补」的反应式设计上（SRS §2 相位定义即如此），
> 健康帝国（库存增长、无赤字）本就不该继续铺区划 —— v1 会把"治理得好"判成"不通过"。
> 方案 B（加主动扩张项）被否：违背补缺意图、与资源相位判断打架、改动面大。
> 舰队健康度不再依赖标量 fleet_size 单独判定，由 R-2 累计计数 `om_ships_built` 交叉确证。
