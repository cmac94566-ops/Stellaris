## 4. 逐堡归属取证（本轮新增方法）

上一轮的取证缺口是「未按国家/星系切分」。本轮补齐 —— **starbase 对象与 system 对象都不带 `owner` 字段**，
归属只能走「行星 → controller → 所属 star system → 该系统的 `starbases={}` 引用」这条链：

1. `gamestate` 顶层 `starbases={}` → 每个对象的 `level` 与 `modules={}` 槽位表；
2. `galactic_object={}`（星系）→ 每系的 `planet=<id>` 列表与 `starbases={ <id> }` 引用；
3. `planet={}` → `controller=<国家 id>`；
4. 某系存在 `controller=0` 的行星 ⇒ 该系归我方（国号由 `overmind_metrics.overmind_country()` 定位 = **0**，与 `player_country` 一致）。

**交叉校验**（同一档，三项独立读数互相吻合）：
`starbase_capacity_used = 1`、`owned_planets` 长度 = 1、`controlled_colonies` = 1 ⇒ 我方为**早期小国**，
星堡总数 = **2**（`start` 系统 43 的首都星港 + 系统 811 的前哨）符合。

> ⚠️ **附注**：`overmind_metrics._starbase_counts()` 的**裸词口径**只适合作**趋势代理**，
> 其 docstring 已自我声明。本轮实证其**不能**用于归属判断（见 §7）。

## 5. 决定性反证：outpost 写入不落盘

我方 2 座星堡（`autosave_2219.01.01`）完整槽位表：

| id | level | `modules` |
|---|---|---|
| 0 | `starbase_level_starport`（首都） | `{0=shipyard, 1=solar_panel_network, 2=trading_hub}` |
| 201 | `starbase_level_outpost` | **`{}`（空）** |

推理链（三步，全部可复核）：

1. **候选集**：守卫为 `has_starbase_size >= starbase_outpost` ∧ `NOT has_starbase_module = shipyard`
   ∧ `NOT has_starbase_module = anchorage`（`:2349-2352`）。首都星港含 `shipyard` ⇒ **被排除**（船坞保护门正确生效）；
   ⇒ **唯一候选 = id 201 前哨**。
2. **窗口内尝试次数**：日志按年窗口统计，**2215.01.01 → 2219.01.01 共 23 次**锚地建造（全期 97 次，其中 93 次在 2219.01 之前）。
3. **结果**：id 201 在 **2215/2216/2217/2218/2219 五档中 `modules` 全为空**，且 2219.01.01 档仍是**全空**。

⇒ 23 次带扣费的写入、星堡全程在册、槽位全空 ⇒ **写入未落盘**。

**两条候选机制**（本轮不能区分，但对处置无影响）：
- **(a) 引擎侧无槽位**：原版 outpost **没有模块槽**（星港 2 槽、星堡 4/6 槽），`set_starbase_module` 对 outpost 为 no-op。
  模块定义里的 `potential = is_normal_starbase`（`00_scripted_triggers.txt:3967`，含 outpost）**只门控建造菜单**，
  不等于程序化写入可落地 —— **这正是 V-6c 假设的推理漏洞**。
- **(b) 写入后被他方重算覆盖**：星堡装配自动重算剥离非升级所得模块。

两者均指向同一处置：**先升堡，再装模块**。

## 6. 副作用：合金泄漏（新缺陷 D-48）

代码形态（`:2360-2367`）：

```
random_owned_starbase = { ... set_starbase_module = { slot = 1 module = anchorage } 
                          log = "OVERMIND: 【锚地】 …" }
add_resource = { alloys = -50 }
```

`log` 与 `add_resource` 都是**无条件**执行，而 `set_starbase_module` **无返回值可判** ⇒
**日志与扣费均不反映真实结果**（典型「空壳日志」形态：有 log、无真实动作）。

- 本会话累计无效扣费：**97 × 50 = 4 850 合金**（约 19 年，对早期小国是量级可观的损失）。
- 与 D-25 的手工扣费约定叠加后，**扣费与效果脱钩**是本缺陷的核心。

### D-48（登记）
- **标题**：V-6 锚地/贸易枢纽——写入静默无效但日志与合金扣费照常（扣费与效果脱钩）
- **级别**：中（资源泄漏 + 谎报日志）；**属地 [zcode]**
- **判据（AC）**：
  - AC-1：修后`【锚地】`行**仅在**目标星堡 `level ≥ starport` 时出现；
  - AC-2：连续年度档中，我方星堡 `modules` 出现 `anchorage` 的**数量增量** ≥ 日志建造数（允许 AI 侧噪声，须同比）；
  - AC-3：无效写入场景下 **不得**再扣合金（闸门置于写入前置条件，而非事后）。

## 8. V-6b 转案（先升堡，再装模块）

原版权威范式：`paragon_effects.txt:1252-1256` —— **先 `set_starbase_size = starbase_starport`，再 `set_starbase_module`**。

**新增约束（本轮实读存档，BACKLOG 旧文未记）**：

| 量 | 实测值 | 含义 |
|---|---|---|
| `starbase_capacity` | **3** | 容量上限 |
| `starbase_capacity_used` | **1** | 当前占用（**outpost 不占容量**） |

⇒ **升堡会消耗容量**：容量余量仅 **2**。若 V-6b 对所有前哨升堡，**必然撞上限** ⇒
规格须新增**容量门**：`starbase_capacity_used < starbase_capacity` 才升堡，且**每条**升堡后重新判定。

**接入点维持既定裁定**：挂 tick 直调段（与 `:2638` 同层），**不挂相位**
—— 避免重演 D-39 零执行 / D-40 熔断饿死。

## 9. 验收判据修订（AC-1..AC-5′，取代 V-6 原 AC-1..AC-7 的 AC-1/AC-6）

| 编号 | 判据 | 口径要点 |
|---|---|---|
| **AC-1′** | 我方星堡 `modules` 中 `anchorage` 计数 **≥1**（口径：§4 归属切片，**非**裸词） | 现值 **0** |
| **AC-2′** | 建造日志数 ↔ 归属切片 `anchorage` 增量**同比**（允许 ±AI 噪声，须同时报银河总量） | 「有无」型判据作废 |
| **AC-3′** | 目标星堡 `level ≥ starbase_starport`（升堡成功后才装） | 原 AC-1 的「`【锚地】` ≥1 次」**不足以**判通过（本轮 97 次全落空） |
| **AC-4′** | 容量门生效：`starbase_capacity_used ≤ starbase_capacity`，且达上限时**不**再试图升堡 | 新增 |
| **AC-5′** | 幂等：同一星堡不重复扣费；`候选=no` **应出现**（全部候选装毕后） | 现值 `候选=no` = **0**，即幂等从未生效 |

**AC-3′ 是本轮最大教训**：上一轮把「日志出现次数」当验收判据，
而日志是**无条件打印**的 ⇒ 判据对「写入无效」**完全失敏**。
**验收判据必须锚定「状态变化」（存档读数），不能锚定「声明」（日志）。**
