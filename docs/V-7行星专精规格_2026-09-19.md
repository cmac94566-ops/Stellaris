## 0. TL;DR（四条）

1. **效果名确证为 `set_colony_type`，不是 `set_planet_designation`。**
   `set_planet_designation` 在引擎效果文档与本机全语料**零命中** ⇒ 照直觉起名必踩 D-8 型命名陷阱。
   合法 scope：`planet / ship / colony`；原版先例 **10 处 / 6 文件**。
2. **读取有两条原语，且都是实读在册**：触发器 `colony_type = col_X`（文档在册）与
   `has_designation = col_X`（**原版 253 处**）。⇒ **幂等判据用 `has_designation` 实时查，零账本**（铁律 20）。
3. **每个专精自带 `potential` 硬门，不满足即静默拒绝** —— 这是与 **D-39 同族**的「静默不生效」失效模式。
   ⇒ 本规格**逐条复刻 potential**，且 **AC-1 必须读 `has_designation` 回读**，不允许只看日志打点（否则重演"有日志≠有效果"）。
4. **零花销、无资源门。** 原版 10 处 `set_colony_type` 调用**零处伴随付费**，引擎文档也无 cost 字段
   ⇒ **明确禁止**给本项加 `overmind_can_afford`（加了才是引入假约束，与 D-25 的记账纪律同源）。

### 1.3 收益本体（为什么要做）

收益不在 `set_colony_type` 本身，而在**专精挂载的两个东西**：

① **产出修正** —— 各专精经 `inline_scripts/colony_types/colony_type_planet_modifier*.txt` 施加
`<job>_jobs_bonus_workforce_mult = 0.15`（传统 `tr_adaptability_finish` 再加 0.05）：

| 专精 id | 施加的修正 | 对应岗位 |
|---|---|---|
| `col_generator` | `technician_jobs_bonus_workforce_mult` | 技工（能源） |
| `col_mining` | `miner_jobs_bonus_workforce_mult` | 矿工 |
| `col_farming` | `farmer_jobs_bonus_workforce_mult` | 农民 |
| `col_foundry` | `foundry_jobs_bonus_workforce_mult` | 冶金师（合金） |
| `col_factory` | `artisan_jobs_bonus_workforce_mult` | 工匠（消费品） |
| `col_industrial` | `artisan_jobs_bonus_workforce_mult` | 混合工业 |
| `col_research` | `researcher_jobs_bonus_workforce_mult` | 研究员 |
| `col_bureau` | `bureaucrat_jobs_bonus_workforce_mult` | 行政（凝聚力/行政容量） |
| `col_city` | `trader_jobs_bonus_workforce_mult` | 商人（贸易值） |
| `col_fortress` | `planet_modifier`（陆军速度 +25%、陆军防御 +20%、兵员 +15%） | 要塞 |

② **AI 建置亲和** —— 每个专精带 `ai_building_set_affinity`（如 `col_foundry` → `foundry = 2.0 / industrial = 1.5`；
`col_research` → `research = 2.0 / physics·society·engineering = 1.5`）。
**这才是专精影响「自动化建什么」的抓手** —— 也是 V-7 与纯装饰性改动的分界线。

### 1.4 `potential` 硬门 + `district_set` 对照（复刻依据）

所有目标专精的 `potential` 都是同一套模板，实读归纳为四条**并列硬门**：

```
potential = {
    owner_or_space_owner? = { is_wilderness_empire = no   is_nomadic = no }      # 帝国形态门
    NOR = { uses_district_set = city_world / ring_world / habitat /
                               machine_world / hive_world / cosmogenesis_world } # 星球类型门
    is_special_colony_type = no                                                   # 特殊殖民地门
    is_capital = no                                                               # 首都门
    NOT = { is_planet_class = pc_nanotech }
}
```

对照证据：

| 概念 | 取值 | 出处（确证） |
|---|---|---|
| 常规宜居行星的 district set | `standard` | `common/planet_classes/00_planet_classes.txt:105/144/183/…`（多行一致） |
| `city_world`= 都市星球（ecumenopolis） | `district_set = city_world` | `common/planet_classes/02_planet_classes_megacorp.txt:42` |
| `is_special_colony_type` | `penal_colony` / `resort_colony` / `slave_colony` 三种 modifier 之任一 | `common/scripted_triggers/00_scripted_triggers.txt:3089` |
| 触发器 scope | `uses_district_set` → planet/ship/colony；`is_capital` → planet/ship/colony | `triggers.log:2625/1067` |
| 帝国形态脚本触发器 | `is_regular_empire` / `is_gestalt` / `is_wilderness_empire` | `00_scripted_triggers.txt:1671/1710/1723` |

⇒ **我方安全子集（R0）**：`uses_district_set = standard` ∧ `NOT = { is_capital = yes }`
∧ `is_special_colony_type = no` ∧ `NOT = { is_planet_class = pc_nanotech }` ∧
`owner = { is_regular_empire = yes }`。
用**正向** `uses_district_set = standard` 作门，比逐个 `NOR` 排除更稳（不必枚举未来新增的世界类型）。

### 1.5 与 vanilla 自动专精的关系（价值边界，诚实说明）

vanilla **已有**自动专精判定：`weight_modifier` 按「已建成 zone / 区划数 / 星球尺寸」打分，
且带 `@stickiness`（当前专精自身加权）⇒ **手动设定会被粘住、不会被自动逻辑回滚**。

但它是**反应式**的：先把球建杂，再贴一个"最像"的标签。
V-7 的增量价值 = **主动定调**：在球刚殖民、区划未铺开时就锁定主业，
从而**提前引导 `ai_building_set_affinity`**（§1.3②），让自动化从一开始就按主业铺。
⇒ **验收必须能区分这两者**：只证明「球上出现了专精」不足以证明 V-7 有效（自动逻辑也会产生专精），
必须证明「**专精与主业一致率**」高于基线（详见 AC-2）。

## 2. 规格（R0–R5，按序落地，一次只动一个变量）

### R0 — 目标集与硬门

- 候选专精（**只用常规行星可用的 9 个**）：
  `col_generator` / `col_mining` / `col_farming` / `col_foundry` / `col_factory` /
  `col_industrial` / `col_research` / `col_city` / `col_bureau`
- 硬门（与 §1.4 一致，须逐条落进 `limit`，**不得靠"试写看引擎报不报错"**）：
  `uses_district_set = standard` · `NOT = { is_capital = yes }` ·
  `is_special_colony_type = no` · `NOT = { is_planet_class = pc_nanotech }` ·
  `owner = { is_regular_empire = yes }`

### R1 — 一球一职映射表（**全部使用原版既有原语，零自造判据**）

按序求值，**先命中先定**（顺序即优先级）：

| 序 | 条件（planet scope） | 目标专精 | 依据 |
|---|---|---|---|
| 1 | `has_any_foundry_zone = yes` ∧ `NOT = { has_any_factory_zone = yes }` | `col_foundry` | `01_scripted_triggers_buildings.txt:944` |
| 2 | `has_any_factory_zone = yes` ∧ `NOT = { has_any_foundry_zone = yes }` | `col_factory` | 同上 `:920` |
| 3 | `has_any_foundry_zone = yes` ∧ `has_any_factory_zone = yes` | `col_industrial` | 混合工业球 |
| 4 | `has_any_generator_zone = yes` | `col_generator` | 同上 `:802` |
| 5 | `has_any_mining_zone = yes` | `col_mining` | 同上 `:858` |
| 6 | `has_any_trade_zone = yes` | `col_city` | 同上 `:1075` |
| 7 | `num_districts = { type = district_generator value >= 3 }` | `col_generator` | `triggers.log:964` |
| 8 | `num_districts = { type = district_mining value >= 3 }` | `col_mining` | 同上；id 见 `02_rural_districts.txt:122` |
| 9 | `num_districts = { type = district_farming value >= 3 }` | `col_farming` | 同上 `:255` |
| — | **其余（无任何主业 zone 且无 ≥3 同类区划）** | **不设** | 见下 |

**兜底为什么"不设"**：无禀赋时强设会**反向误导 `ai_building_set_affinity`**（让自动化去铺该球并不适合的产业）。
留 vanilla 自动判定更优 —— 符合 A3「看收益」。**这是取舍，不是遗漏**；若后续实机显示"杂球"数量大，再单独裁。

> **我方不预设的是"何时设"**：R1 只回答"设成哪个"。**殖民后多久内必须定调**属策略参数，交由 S-20 规则集/年代门决定（见 R4）。

### R2 — 幂等（实时查，零账本）

写入前必须回读：
```
if = { limit = { NOT = { has_designation = <目标> } }  set_colony_type = <目标>  log = … }
```
- **禁止**新建 `om_designated_*` 类旗标/计数（铁律 20：不写影子账本）。
- 抗振荡说明：vanilla 不拆已建区划 ⇒ 主业不会月度漂移；
  叠加 `@stickiness`（§1.5）⇒ 已定调球不会被自动逻辑改回。**该抗振荡结论标「待验」（见 §5）。**

### R3 — 选点

`random_owned_planet = { limit = { <R0 硬门> } … }` —— 与既有相位实现同范式
（`overmind_autonomy.txt:78/102/125/…` 共 20+ 处先例）。
**每月最多处理 1 球**（`random_owned_planet` 天然如此），天然限速，不额外加节流参数。

### R4 — 接入点：**挂 tick 层「每月必做」，不挂相位**

**理由（本项目三连教训）**：相位通道会被 **S-18 规则集**（3 并行槽 + 规则序号先到先得）
与 **D-40/D-41 熔断**吞掉 —— D-39（V-6 零执行）就是挂在相位里被饿死的直接受害者。
⇒ V-7 若再挂相位，**大概率重演"零执行"**。

推荐位置：与既有 `overmind_autonomy_manage_leaders`（`overmind_autonomy.txt:2638`）
**同层**的 tick 直调段。**层级预算**：具体余量由 zcode 依 `tests/test_bridge.py` 复核
（我方不预设层数结论 —— 该文件正在被改，行号与时值均为在途，不引用）。

### R5 — 日志与降噪

- 只在**实际写入时**打一行：`OVERMIND: 【专精】 <col_id> —— 一球一职（主产区已识别）`
- **禁止**：每月无条件打点（那是空壳日志，铁律 20）；**禁止**打印星球名
  （避免 `[...GetName]` 宏族陷阱 —— 既有 D-21 "Invalid macro entry … his.GetName" 即此族）
- 量级自检：稳态下应为 **0–N 行/局**（N = 新殖民球数），而非每月 1 行。
  ⇒ **日志行数本身就是 AC-3 的自证指标**。

## 3. 验收标准（AC-1..AC-7）

| # | 判据 | 通过线 | 取证方式 |
|---|---|---|---|
| **AC-1** | **回读有效**（不是"打过日志"） | 至少 1 个球 `has_designation = <目标>` 为真 | 日志有 `【专精】` 行 **且** 游戏内行星面板专精显示为目标（**双源**） |
| **AC-2** | **主业一致率**（区分"我方定调"与"vanilla 自动"的关键） | 被写入的球中，专精与 R1 主业一致率 **100%** | 逐条核对日志 `<col_id>` vs 该球 zone/区划 |
| **AC-3** | **无空壳/无噪音** | `【专精】` 行数 ≈ 新定调球数（**不为月数**）；连续月无重复行 | `grep -c '【专精】'` 对比新殖民球数 |
| **AC-4** | **无静默失败** | `error.log` 中涉 `colony_types` / `set_colony_type` 的报错 **= 0**；且**不存在**"打了 `【专精】` 但回读为假"的球 | `error.log` grep + 面板抽验（≥3 球） |
| **AC-5** | **不误伤特殊球** | 首都 / 特殊殖民地 / 非 `standard` district set 的球**零写入** | 逐条核对写入目标的 scope 条件 |
| **AC-6** | **零花销** | 代码中该项**无** `overmind_can_afford` / `add_resource` 负项 | 代码审（5 层预算核对同时做） |
| **AC-7** | **不触层级上限** | `test_bridge.py` 守卫通过；嵌套深度 ≤ 既有 tick 直调段 | pytest 基线 + 守卫 |

**十年窗口径（沿用 D-41 订正后的纪律）**：AC-2/AC-5 至少覆盖 **10 年**且**同一局内连续**（铁律 18）；
异局档、缺口年份一律剔除并标注。

## 6. 与 D-39 / D-40 / D-41 的关系（同族但不同层）

| 缺陷 | 失效机制 | V-7 的对应防线 |
|---|---|---|
| **D-39**（V-6 星港模块零执行） | 门写严（`>= starport`）与现状（全 outpost）恒不匹配 ⇒ **静默不生效** | R0 逐条复刻 `potential`；AC-1 要求**回读**而非只看日志 |
| **D-40**（熔断活锁） | 相位通道被规则集饿死 | R4 **不挂相位**，挂 tick 直调段 |
| **D-41**（熔断不可解除） | 状态写入不回收 ⇒ 长期降级态 | V-7 **不写任何状态**（零账本）⇒ 结构上不可能产生同族死锁 |

**一句话**：V-7 的设计目标是**不重犯这三个坑** —— 门要复刻、通道要选对、状态要零。
