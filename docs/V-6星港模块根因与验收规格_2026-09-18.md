## 0. 一句话结论

**V-6 代码语法、模块 id、scope 全部正确，但结构上不可达** ——
其 `limit` 首条要求 `has_starbase_size >= starbase_starport`，而我方自治层
**只建 outpost（前哨站）、全库无任何升堡调用** ⇒ 该门**恒假** ⇒
两个分支**从未执行过一次**。

而原版已有权威范式：**对 outpost 先 `set_starbase_size` 升级、再装模块**
（`paragon_effects.txt:1252-1256`）—— V-6 **恰好缺这一步**。

## 2. 根因链（确证）

### 2.1 卡点：V-6 自设的 size 门

`overmind_autonomy.txt:2155-2182` 两分支的 `limit` 首条均为：

```
has_starbase_size >= starbase_starport
```

### 2.2 我方星堡实际全是 outpost

| 证据 | 内容 |
|---|---|
| `create_starbase` 调用点 **2 处**，均为 outpost | `overmind_autonomy.txt:2269-2272`（重建边境前哨站）`size = starbase_outpost`；`:2981` 拓土建站同款 |
| 全库**无升堡调用** | `grep -rn "upgrade_starbase\|set_starbase_size" mod/stellaris_overmind/` **零命中** |

⇒ 我方全部星系只有 **outpost** ⇒ `>= starbase_starport` **恒假** ⇒ V-6 **永不进入**。
**本局 139 月 × 2 分支 = 约 278 次尝试，成功 0 次。**

### 2.3 关键反证：卡点**不是引擎限制**，纯粹是门写严了

原版 `is_normal_starbase` 定义（`00_scripted_triggers.txt:3967`）：

```
is_normal_starbase = { has_starbase_size >= starbase_outpost }
```

而两块模块的 `potential` 均为 `is_normal_starbase = yes`
（`00_starbase_modules.txt:91-93` anchorage、`:365-367` trading_hub）。

⇒ **outpost 本身就满足模块装载 potential**，锚地/贸易枢纽**本可装在 outpost 上**。
V-6 把门设到 `starbase_starport` **是自我否决**，非引擎边界。

### 2.4 原版权威范式：先升级、再装模块

`common/scripted_effects/paragon_effects.txt:1250-1259`：

```
if = {
    limit = { has_starbase_size = starbase_outpost }
    set_starbase_size = starbase_starport          # ← 先升级
    set_starbase_module = { slot = 1 module = shipyard }
    set_starbase_module = { slot = 2 module = shipyard }
}
else_if = {
    limit = { NOT = { has_starbase_module = shipyard } }
    set_starbase_module = { slot = 1 module = shipyard }
}
```

**这正是 V-6 缺失的一步**：原版对 outpost 的处理是**就地升级为 starport** 后再装模块。
`set_starbase_size` 原版用法丰富（`paragon_effects.txt:1252/1335/1970/2048`、
`nomads_effects.txt:193`、`marauder_scripted_effects.txt:1123/1170`、
`02_machine_age_effects.txt:2532` 升到 citadel）——**形态确证**。

### 2.5 已排除的错误方向（留痕，避免重走）

- ❌ **不是** module id 写错：原版 `module` 值**不带 `starbase_` 前缀**
  （`02_machine_age_effects.txt:2534` `module = anchorage` 先例；代码写作 `anchorage` / `trading_hub` —— **正确**）。
  两块模块定义在册：`anchorage`（`00_starbase_modules.txt:85`）、`trading_hub`（`:359`）。
- ❌ **不是** `random_owned_starbase` 非法：原版 **38 处**命中，合法 scope。
- ❌ **不是** 缩进问题：Clausewitz 不敏感缩进，且 error.log 零语法报错。

## 3. 修法（交 zcode 实现）

**方案 V-6b（推荐，原版同款）**：把 V-6 的 limit 依赖从「已是 starport」
改为「**是 outpost 也照样处理**」，块内补升级：

```
random_owned_starbase = {
    limit = {
        NOT = { has_starbase_module = shipyard }     # 硬底线：不覆盖船坞
        NOT = { has_starbase_module = anchorage }    # 幂等
        overmind_can_afford_xxx = yes                # 花销走既有预算门（见 §4 约束）
    }
    if = {
        limit = { has_starbase_size = starbase_outpost }
        set_starbase_size = starbase_starport         # 原版范式
    }
    set_starbase_module = { slot = 1 module = anchorage }
    log = "OVERMIND: 【锚地】 星堡补锚地模块 —— 海军容量提升"
}
```

**要点**：
1. `set_starbase_size` 与锚地模块（**50 合金**，`00_starbase_modules.txt:96-100`）**必须接 `overmind_can_afford`**，
   否则绕过预算门（同 D-25 的手工扣费约定）。
2. 升级到 starport 会**改变星系军事属性**（星堡有武器/HP）⇒ 需评估「是否会被 A2 多线并行牵连宣战」，
   并在规格中给出取舍理由（可保守：只对**星区首府/枢纽星系**升级）。
3. 若判定升级代价过大 ⇒ **备选 V-6c**：直接对 outpost 装模块（2.3 已证 potential 允许），
   **不升级**。此路径更省合金，但需先实机验证 outpost 装载锚地**是否真生效**
   （potential 满足 ≠ 效果无条件成立；建议 zcode 用一次性探针验证后再选）。
4. `trading_hub` 分支同款处理；注意其模块定义带 `initial = yes`（`:363`）。
